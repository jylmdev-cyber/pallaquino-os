# ADR-0014: Cliente MCP propio en la stdlib para la revisión 2026-07-28, con compatibilidad legacy explícita

- Status: accepted (2026-10-14, v0.5.0)
- Confidence: high. La interoperabilidad con el SDK oficial `mcp` 2.3.0 se verificó en las dos direcciones, stdio y Streamable HTTP, moderno
  y legacy (ver `docs/evaluation/MCP_CONFORMANCE_REPORT.md`)
- Context:
  - El pedido fija como objetivo la especificación MCP 2026-07-28, consultada el 2026-10-14 en modelcontextprotocol.io: sin `initialize`
    ni sesiones, `_meta` por petición, `server/discover`, `resultType`, MRTR, cabeceras `Mcp-Method`/`Mcp-Name`/`Mcp-Param-*` y Tasks como
    extensión.
  - El SDK oficial de Python la soporta desde la línea 2.x (PyPI: `mcp` 2.3.0, 2026-10-02). El SDK instalado en este equipo es 1.26.0 y
    solo llega a 2025-11-25.
  - El SDK 2.x depende de pydantic, starlette, uvicorn, httpx2, opentelemetry-api, pyjwt y otros paquetes.
- Options:
  - (a) adoptar el SDK oficial: mejor interoperabilidad; rompe la política de dependencias (solo stdlib, offline, CI sin red) y obliga a
    gestionar un árbol grande;
  - (b) cliente propio con la stdlib, ceñido al protocolo de cable de 2026-07-28, con servidor de referencia para pruebas y una prueba de
    interoperabilidad opcional contra el SDK oficial cuando esté instalado;
  - (c) mezclar revisiones (handshake de 2025 con campos de 2026): explícitamente prohibido por el pedido.
- Decision: (b).
  - Al conectar, el cliente sondea con `server/discover`:
    - un `DiscoverResult` o un error moderno reconocido identifica un servidor moderno;
    - cualquier otro error, o la falta de respuesta, identifica un servidor legacy, que solo se usa con `mode="auto"`.
  - Ante `UnsupportedProtocolVersionError` (-32022) se reintenta con una versión común.
  - **Transportes**:
    - stdio: un mensaje por línea; cancelación con `notifications/cancelled`; cierre por stdin, luego terminate y luego kill;
    - Streamable HTTP: POST por mensaje, respuesta JSON o SSE por petición; cancelación cerrando el stream; dirección fijada por la
      política de red (ADR-0016).
  - **Lo que el cliente valida**:
    - nombres y esquemas de herramienta: se excluyen las inválidas;
    - anotaciones `x-mcp-header`;
    - argumentos contra `inputSchema` y `structuredContent` contra `outputSchema`;
    - tamaños de respuesta;
    - `resultType`: si falta se trata como `complete`; si es desconocido, el resultado es inválido.
  - **MRTR**: el manejador por defecto deniega toda petición de input, de modo que un servidor no puede obtener datos ni aprobaciones sin
    el control central.
  - **Extensión Tasks**: opt-in por conexión. Hace polling de `tasks/get` respetando `pollIntervalMs`, cancela al vencer el plazo y
    mantiene la referencia de tarea externa separada de la tarea de PALLAQUINO.
  - **No implementado**: `subscriptions/listen`, Roots, Sampling y Logging (los tres en desuso en 2026-07-28) y el transporte HTTP+SSE de
    2024.
- Consequences:
  - Funciona offline y sin dependencias. La conformidad está probada contra el servidor de referencia propio, que comparte la lectura de la
    especificación; por eso existe además la prueba contra el SDK oficial, que pasa con `mcp` 2.3.0.
  - El catálogo se revisa y se fija antes de usarse (ADR-0015).
- Reversal: `McpClient` tiene una interfaz pequeña (`connect`, `list_tools`, `call_tool`, `read_resource`, `get_prompt`). Un adaptador
  sobre el SDK oficial puede sustituirlo sin tocar la pasarela.

Resumen de `CONTRIBUTING.md`. Ante cualquier diferencia, manda ese archivo.

## Antes de empezar

Busca o crea un Issue con el problema, el alcance y el criterio de aceptación. Los cambios de arquitectura, seguridad, registros o
contratos públicos se acuerdan primero en el Issue.

## Validaciones obligatorias

Desde `universal_ai_fullstack_orchestrator`:

```bash
python -m unittest discover -s tests -v
python -m pallaquino_cli validate --integrity-only
python scripts/architecture_fitness.py
python -m pallaquino_cli security audit --target ..
python -m compileall -q pallaquino_cli scripts tests
```

<Aside>
	Con tu propia identidad usa `--integrity-only` y **no modifiques** `governance/git_identity.json` en tu pull request: la comprobación de
	identidad del repositorio la aplica la CI.
</Aside>

## Convenciones

- Ramas `feat/…`, `fix/…` o `docs/…`; un propósito por pull request.
- Commits con prefijo: `feat:`, `fix:`, `docs:`, `test:`, `refactor:`, `perf:`, `build:`, `ci:` o `chore:`.
- Los trailers de coautoría de IA están prohibidos.
- JSON en UTF-8 con dos espacios; Markdown con enlaces relativos y ejemplos ejecutables.

## Qué explica un pull request

Qué problema resuelve y por qué; qué archivos, contratos y rutas afecta; riesgos, seguridad, migración y rollback; comandos ejecutados y
resultado de los gates; evidencia cuando cambia algo visible.
